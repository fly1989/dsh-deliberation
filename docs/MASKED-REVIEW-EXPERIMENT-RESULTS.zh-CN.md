# Masked Review 配对实验：结果、发现与避坑记录

日期：2026-11-18。本文是 2026-11-07 至 11-17 这一轮本地实验的收尾记录。它不是效果声明，也不改变插件的默认行为。研究假设本身见 [MASKED-REVIEW-RESEARCH-NOTES.zh-CN.md](MASKED-REVIEW-RESEARCH-NOTES.zh-CN.md)。

> **一句话**：在已有的样本中，没有观察到“隐藏 reasoning”带来稳定收益，也出现过有害反馈。原始想法没有被证伪，但也没有得到公平的检验。更值得记住的，是失败具体发生在哪一环，以及哪些实验做法会让结论失真。

文中的标签沿用研究主文档：**本地观察**是本轮实际看到的行为，不能外推；**研究假设**是尚未被验证的主张。

## 1. 测了什么

所有效果实验都用同一个设计：从一段真实的 Primary 轨迹构造一份合成的 user 文档，交给 review child。两组文档只差一点：保留组在文档里附上已记录的 reasoning（`retain-reasoning`），隐藏组省略它（`reasoning-only`）。两组的系统提示、审查任务、JSON 协议、工具和模型都相同。

| 记录 | 题目与断点 | 对照 | 本地观察 |
| --- | --- | --- | --- |
| E1 | SWE-bench Pro 的 Ansible multipart 题；错误候选在预算耗尽时停下（45/46）；另有一个正确候选（46/46） | 每个候选两组各 2 次；对 update 另做 9 次 Primary 续跑 | 错误候选上，保留组 0/2、隐藏组 2/2 发布 update；续跑 9/9 仍是 45/46。正确候选上四次都是 no_update |
| E2 | AnyIO 取消竞态，Step 47：已经复现、尚未改源码 | 三组：不审查、保留、隐藏，各 1 次；另做对第 6 条的消融 | 不审查组 62/62（三次尝试里唯一留下补丁的一次），保留组 62/62，隐藏组 58/62 |
| E2b | 同一 AnyIO 题，Step 48：库补丁已经正确 | 每组 2 次审查，加 4 条续跑 | 四条续跑都补了有效的回归测试；隐藏组的两条续跑还补了 changelog |
| E3 | 与 E1 同一道题，自然完成时已经是 46/46 | 每组 1 次 | 隐藏组采纳了一条防御性修改，结果不变 |
| E5、E6 | 导入的 SWE-smith 轨迹，没有仓库工具 | 每组 1 次 | 全部没有增量；E6 用的是另一套分类提示，不能代表生产提示 |
| E4 | urllib3 303 | — | **答案泄露，作废**（见第 3.1 节） |
| PR bench | 五个静态 PR | 生产提示 vs 普通提示 | **不是 mask 实验**：两组都保留 reasoning，而且这些 PR 本来就没有 reasoning |

需要注意：有效记录实际上只来自**两道题**。同一题的重复运行不算独立样本。

## 2. 发现

### 2.1 隐藏 reasoning 改变的是“报不报”，不是“想不想得到”

**本地观察**。E1 中，“body 不该带顶层头”是唯一指向真实失败的疑点。逐句阅读 child 的 recorded reasoning 后发现：

- 4 个 child **全都考虑过**这个疑点，只有 1 个隐藏组 child 把它作为 uncertain 发布了。
- 两个保留组 child 不发布的理由是：题面字面上支持完整 MIME、模型记得上游实现就是这样、给不出可行的检查，再加上提示规则带来的克制。其中一个自评 “~75% full is right. So no.”
- 两个保留组 child 都**没有**把“Primary 已经讨论过”当作理由，反而说 actor “did not question”。

E2b 的 changelog 也类似：保留组也有一个 child 想到了，但以“用户没要求”为由否决。

因此，“隐藏组发布了、保留组没发布”不能写成“隐藏组发现了保留组想不到的东西”。另外需要提醒：reasoning 里没有出现，也不等于模型想不到；reasoning 里出现一句正确的猜测，也不等于模型有能力把正确方案做出来。

### 2.2 失败多发生在“裁决”这一环

**本地观察**（两道题，样本很小）：

- **争议点靠推理或记忆拍板。** E1 的契约有歧义，仓库里也没有 fixture 或调用方能裁决。Primary 在原轨迹和 6 次带反馈的续跑中，都靠推理选了完整 MIME，没有一次说“目前无法判定”。
- **检查执行了，但区分不了。** 续跑时 Primary 写的自测，是拿实现自己的构造方式去验证实现。免费交叉检查发现：这个自测在错误实现上通过，在正确实现上反而报错。它制造了虚假安心。
- **未经检验的排除或排他断言被当成定论。** E1 中，Primary 用一句没验证过的解释（“should match. Not issue.”）打发了一个反常结果。E2 中，隐藏组断言“在 release 里提前清理必然破坏旧测试”，这一点从未被检验，而且有直接反例；Primary 照做，结果 58/62。原 packet 2 次都失败，删掉这一条后 1 次通过。

看起来，“产生候选”并不是最常断的地方。如何让一个备选解释**获得裁决**，以及判定不了时该怎么办，更值得研究（**研究假设**）。

### 2.3 一条清楚的取证链条

**本地观察**。E2b 中，一个隐藏组 child 起初也认为 changelog “Not decision-critical”。随后它去读了 Primary 从没读过的 `AGENTS.md`，拿到了明确的仓库要求，于是发布；Primary 续跑时又自己核对了一遍并补上。

链条是：已有候选 → 读取此前没看过的文件 → 依据变得更可靠 → 实际交付。

这只有一次，不能说明它是 mask 带来的；同一组的另一个 child 没有读任何文件、只凭“仓库惯例”也提了 changelog。它展示的是：额外计算可以通过拿到**更可靠的依据**来支撑决策。但“多读文件”不是万能解释：E1 里根本没有可读的裁决证据。

### 2.4 提示规则和输入表示会让两组的发布门槛不对等

**实现事实**：

- 保留组的 reasoning 被渲染在 `Assistant visible content:` 标签**之下**；隐藏组没有任何“此处已省略”的标记。
- 审查提示写着：复述 “a visible Primary conclusion” 不算 delta，并要求先和 “Primary-visible history” 比较。

后果是：同一个疑点，在保留组里可以被看成“复述了 Primary 的讨论”，在隐藏组里却是 child 自己的新判断，两组的“已知内容”不同。规则也没有区分“这个事实已经出现过”和“这个事实仍然反驳当前结论”。日志里能看到 child 卡在这个分类上。

这一点在结构上成立，但它是否就是 E1 两组差异的原因，**无法区分**：没有做过“保留 reasoning + 修改规则”的对照。

### 2.5 其他值得记住的观察

- **certainty 自报不可靠**：E2 的一条错误结论被标成了 certain。
- **有害反馈是真实存在的**，不能宣传“最坏也没有负收益”。
- **update 数量不等于召回**，条目数量也不等于发现数量：E2b 中一个 7 条的 packet，大部分是复述。
- **只看 packet 会误判**：child 的 recorded reasoning 是关键的分析材料。

## 3. 避坑清单

### 3.1 评测隔离

- E4 中，Primary 的 bash 能访问实验仓库的根目录，读到了写着修法和隐藏验收测试名的冻结案例文档，以及 runner 正在写入的 results.json。这段工具输出又进入了两组 reviewer 的输入。
- 给 child 的读取工具加路径限制，修不好已经进入父历史的污染。
- 运行前要用 Primary **和** child 的实际工具各做一次路径探针，确认读不到参考修复、隐藏测试、评测日志和其他运行的结果。

### 3.2 样本

- 自然完成、而且已经正确的样本，没有可以观察的纠错空间（E3、E2b、GPX）。
- 预算耗尽时停下 ≠ 自然停止 ≠ “基于错误判断改坏了代码”的中途断点。
- 真正需要的样本，是 Primary 基于错误判断修改了产品代码、而且中途状态能可靠恢复的断点。这类样本很难找：本地缓存的 8 条 SWE-smith 轨迹里一条都没有，最后因为没有合格样本而停止。
- **找样本和采集 Primary 轨迹**往往才是主要成本，预算必须把它算进去。
- 所有分歧对都来自同一道需求有歧义的题，不能推广。

### 3.3 设计与统计

- 先在看到任何输出之前，冻结真值说明、匹配规则和提示，并计算 hash；看过结果再改，就要作废重跑。
- 对称统计：隐藏独有、保留独有、共同候选、错误候选都要统计，并写明核实依据。不要只找隐藏组赢的那一条。
- 区分“重新解释已有信息”和“读到了新信息”。
- 判断 child 的输出时，不要以修好率作为唯一指标；还要看依据是否更可靠，以及是否支持了后续选择。正确地保留原方案、避免一次错误修改，也算收益。
- 不要用旧样本调提示，再把结果当作独立验证。

### 3.4 已实现但没被测到的部分

- 所有效果实验里，更早的已完成 Turn（H）都是空的，窗口一律是 `current-turn`。非空 H 和 `recent-steps`（K）都没有被测过。
- 两组都用合成文档；“原生历史回放 vs 改写后的执行记录”从来没有对照过。
- 实验 runner 用的是最小 kernel，不是完整的 Web profile。

### 3.5 容易说过头的地方

- 模型自评的“75% 把握”不是采样概率；reasoning 里最后选了一个解释，也不等于解码器“杀掉了概率尾巴”。
- RL 让探索变窄是一个有证据的现象，但不是通则；不能借此反推某个模型具体被压住了什么能力。
- DeepSeek thinking 模式不使用 `temperature`，调温度增加多样性这条路行不通。

## 4. 当前状态

- 运行时、child 启动、结构化反馈和 Primary 续跑都已经实际运行过。
- mask 效果线就此收尾：没有观察到稳定收益，有过负收益，有一组被污染。
- 自动审查继续默认关闭；masked-review 保持实验定位。
- 暂缓 reasoning 长度分布、动态切点和熵触发的研究。
- 如果以后继续，建议的问题是：在同一前缀下，少量额外探索能否获得更可靠的依据，并支持更好的下一步选择？mask、反事实提示、换模型都可以作为探索手段，但不要事先认定哪一种有效。
- 如果日常使用中**自然出现**了一个合格断点（基于错误判断改坏了产品代码，状态可以恢复，没有泄露），可以低成本做一次最小对照：两组用同一个探索型提示，盲标，对称统计。不建议为了得到这样的样本主动大规模筛题。

## 5. 不能据此下的结论

- “mask 无效”或“mask 有效”；
- “保留组想不到某个问题”；
- “改提示词就能替代 mask”；
- “问题都出在模型本身”；
- 任何关于成本、延迟或缓存收益的结论。

## 6. 材料位置

实验 runner 在本地的 `experiment/*` 分支上，没有合入 main。原始 session、补丁和验收日志保存在被忽略的本地 `.cache/` 目录，含有完整的模型轨迹，不随仓库发布。本文的每一条观察都来自对这些原始记录的逐句复核，而不是只看汇总报告。
